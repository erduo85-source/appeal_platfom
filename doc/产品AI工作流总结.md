# 产品 AI 工作流总结

## 一、适用场景

本文沉淀自「游戏接入配置」完整协作链路，以及两个相关历史对话：

- 文档编写：通过本地 Markdown、截图和在线文档完成需求文档整理与写入。
- 评审修改：读取评审记录，拆解修改计划，并同步更新需求文档、设计稿和代码原型。

适用于产品经理在本地使用 AI 完成以下工作：

| 场景 | 目标产物 |
| --- | --- |
| 需求构思 | 设计思路、交互方案、问题清单 |
| 设计推进 | Figma frame、状态页、弹窗/抽屉/确认态 |
| 需求文档 | 可评审、可交付的 PRD/需求说明 |
| 原型实现 | 可本地预览、可 GitHub Pages 访问的静态原型 |
| 评审修改 | 评审记录、修改计划、需求/设计/代码同步 |
| 在线文档写入 | 钉钉在线文档、富文本表格、截图说明 |

## 二、核心原则

| 原则 | 说明 |
| --- | --- |
| 先结构化，再生成 | 先把背景、目标、流程、状态、字段、边界拆清楚，再进入设计或代码。 |
| 单一事实源 | 每个阶段必须明确以哪个材料为准，例如“以最新 Figma 设计稿为准”或“以评审记录为准”。 |
| 变更可追踪 | 评审意见不要直接散落在对话里，应整理成修改计划表，并标记需求、设计、代码三个方向的处理状态。 |
| 需求、设计、代码同步 | 任一侧变化后，都要检查另外两侧是否需要同步，避免“设计已改、代码未改”或“代码已改、文档仍旧”。 |
| 本地先验证 | 原型变更后优先本地构建、浏览器预览、截图自检，再考虑提交和发布。 |
| 不伪装完成 | 没有运行、没有截图、没有读取设计稿或没有提交，就明确说明未完成或未验证。 |

## 三、推荐端到端流程

### 1. 需求输入与问题澄清

目标是把用户的自然语言需求转成可执行的产品任务。

| 步骤 | AI 应做什么 | 产物 |
| --- | --- | --- |
| 读取背景 | 理解现有页面、截图、业务限制、目标用户 | 背景摘要 |
| 识别范围 | 判断是需求方案、设计稿、原型代码还是文档整理 | 工作范围 |
| 提出关键问题 | 只问影响方向、数据、权限、交互结果的问题 | 问题清单 |
| 明确阶段目标 | 例如“先整理设计思路，确认后写入 Figma” | 阶段计划 |

本项目中的有效做法：

- 先评估「游戏接入配置」方案，而不是直接写代码。
- 在进入开发前，先整理设计思路并由用户确认。
- 对关闭二次确认、滚动条、多状态页面等补充需求及时纳入后续设计与实现。

### 2. 设计思路整理

目标是把需求转成可写入 Figma 的设计结构。

建议表格结构：

| 序号 | 模块 | 功能描述 | 备注 |
| ---: | --- | --- | --- |
| 1 | 页面入口 | 页面标题区域新增“游戏接入配置”按钮 | 明确入口位置和权限 |
| 2 | 右侧抽屉 | 展示配置提示、游戏列表、底部保存操作 | 明确宽度、遮罩、关闭逻辑 |
| 3 | 配置列表 | 支持拖拽排序、编辑、删除、滚动查看 | 表头和字段要提前固定 |
| 4 | 新增弹窗 | 项目选择、展示游戏名、保存校验 | 明确默认值和错误提示 |
| 5 | 二次确认 | 删除、关闭、保存均有确认态 | 明确是否影响暂存数据 |

注意点：

- 后台管理页面应优先清晰、紧凑、可扫描。
- 抽屉、弹窗、确认框必须补全状态，不只画默认态。
- 表格过长、文字过长、按钮禁用、无数据、保存失败等状态需要提前写入说明。

### 3. Figma 设计推进

目标是把设计思路转成可评审的高保真设计稿。

| 步骤 | 操作 | 验收点 |
| --- | --- | --- |
| 读取现有 frame | 先复用已有后台页面背景和布局 | 不重新造主页面结构 |
| 新增设计 frame | 在已有页面基础上增加遮罩、抽屉、弹窗 | 与原后台视觉一致 |
| 补齐状态页 | 新增、编辑、删除确认、关闭确认、保存确认 | 评审时能覆盖完整流程 |
| 读取用户更新 | 用户手动改稿后，AI 重新读取设计稿总结差异 | 不凭旧记忆继续实现 |
| 多 frame 同步 | 检查主状态和多个确认/弹窗状态是否一致 | 避免只改一个页面示例 |

本项目中踩过的点：

- 抽屉警告条需要按设计稿单行展示，不应擅自换行。
- 字段名从“项目映射”回到“项目选择”后，代码和文档也必须同步。
- 一条配置多个 appid 后，设计稿、代码和需求文档都要统一为 `首个 appid +N` 的折叠展示。

### 4. 原型代码实现

目标是生成可点击、可预览、可发布的静态原型。

| 步骤 | 操作 | 验证 |
| --- | --- | --- |
| 搭建工程 | 使用 Vite + React 创建静态原型 | `npm run dev` 可访问 |
| 还原主页面 | 顶部导航、侧边栏、筛选区、列表 | 与设计稿布局一致 |
| 实现核心交互 | 抽屉、弹窗、二次确认、拖拽排序、搜索多选 | 流程可走通 |
| 使用本地素材 | 游戏 icon 使用 `pic/` 下文件 | 图标真实展示 |
| 本地自检 | 浏览器检查无遮挡、无异常换行、无空白 | 截图或 Playwright 验证 |
| 构建验证 | 运行 `npm run build` | 构建通过 |

实现阶段的经验：

- 后台原型不追求复杂架构，优先保证流程闭环。
- Mock 数据应尽量贴近真实口径，例如使用 `game_list.md` 和本地 icon。
- 每次 UI 反馈都应快速修复并本地验证，而不是只改代码不看页面。
- 服务端口要固定，例如 `5174`，避免预览地址和实际服务不一致。

### 5. 需求文档编写

目标是把产品逻辑沉淀为可评审、可交付、可追溯的 Markdown 文档。

推荐结构：

```markdown
# xxx-需求文档

## 一、需求背景

## 二、需求描述

### 1. 用户流程

### 2. 页面说明
```

页面说明建议覆盖：

| 要点 | 说明 |
| --- | --- |
| 操作流程 | 用户从入口到保存的完整路径 |
| 判断逻辑 | 是否有未保存内容、是否允许保存、是否整体提交 |
| 页面字段 | 主页面、抽屉、列表、弹窗、确认框字段 |
| 特殊状态 | 空列表、加载失败、保存失败、无权限、列表过长 |
| 错误提示 | 必填、重复、跨账号体系、保存失败 |
| 数据来源 | 平台服务中心、后台配置服务、本地 mock |
| 数据排序 | 列表拖拽顺序、下拉数据排序 |
| 边界值 | 0 条数据、过长文本、多 appid、多选 |
| 默认值 | 默认页面、默认筛选项、默认项目选择 |
| 交互效果 | 抽屉遮罩、固定表头、hover tooltip、二次确认 |

本项目中的文档修正点：

- 文档标题从“游戏列表配置”统一为“游戏接入配置”。
- 关闭确认从“清除编辑内容”统一为“重置编辑内容”。
- 错误提示从“请输入展示游戏名称”统一为“请输入展示游戏名”。
- 排序影响范围从“玩家申诉时”扩展为“玩家申诉/找回时”。
- LOGO 上传规则删除，统一改为读取平台服务中心“项目概览”。

### 6. 在线文档写入

目标是把本地 Markdown 和截图稳定写入钉钉在线文档。

推荐流程：

| 步骤 | 操作 |
| --- | --- |
| 准备本地 Markdown | 先在本地把结构、表格、截图路径整理好 |
| 转为富文本 | 将 Markdown 转成 HTML，保留标题和表格 |
| 小段测试 | 在线文档先粘贴一小段，确认焦点正确 |
| 全量粘贴 | 写入 `text/html` 和 `text/plain` 后粘贴 |
| 验证结构 | 检查右侧大纲、章节、表格、图片 |
| 补图片描述 | 选中图片，点击悬浮工具栏 `T`，直接输入描述 |

注意：

- 在线文档虚拟渲染时，DOM 不一定包含全文，验证要结合大纲、搜索和截图。
- 大段粘贴前必须确认正文焦点，否则容易粘贴失败或落错位置。
- 表格密集文档优先用 HTML 粘贴，不建议逐行手写。

### 7. 评审与修改计划

目标是让评审意见可执行、可追踪。

评审修改计划建议表头：

| 序号 | 建议 | 需求文档变更 | 设计稿变更 | 代码实现变更 | 备注 |
| ---: | --- | --- | --- | --- | --- |

处理规则：

| 类型 | 处理方式 |
| --- | --- |
| 只影响需求 | 直接更新需求文档 |
| 影响视觉/交互 | 先更新设计稿，确认后再改代码 |
| 影响字段/数据 | 同步更新需求、设计、代码和 mock 数据 |
| 暂不处理 | 明确标记“未完成”或“不调整”，写清原因 |
| 用户直接改设计稿 | 先读取设计稿，总结更新项，再同步文档和代码 |

本项目中的典型评审变更：

| 评审点 | 最终处理 |
| --- | --- |
| 接入项目数据源 | 改为平台服务中心项目列表 |
| 权限范围 | 本期仅 SDK 内部使用 |
| 切换维度 | 用户与开发确认使用账号体系 |
| 项目选择 | 搜索多选下拉，已选态使用 Ant Design 多选 Select tag 样式 |
| 弹窗主按钮 | 新增/编辑弹窗底部主按钮为“确认”，抽屉底部主按钮继续为“保存” |
| 删除确认 | 删除二次确认弹窗主按钮为“确认”，删除只进入抽屉暂存，最终随抽屉保存生效 |
| 苹果验单配置 | 验证苹果订单默认关闭；开启后才展示苹果包名、KeyID、IssuerID、PrivateKey |
| 多 appid | 一条配置可映射多个 appid，列表折叠展示 |
| LOGO 配置 | 弹窗不再上传，读取项目概览 LOGO |
| 保存范围 | 抽屉内新增、编辑、删除、排序整体提交 |

### 8. 发布与回归

目标是确保本地原型和 GitHub 预览可用。

| 步骤 | 操作 |
| --- | --- |
| 本地构建 | `npm run build` |
| 本地预览 | 固定端口启动，例如 `npm run dev -- --port 5174 --strictPort` |
| 浏览器检查 | 打开 `http://localhost:5174/`，验证核心流程 |
| 提交代码 | 只提交相关文件，忽略 `.idea/` 等本地配置 |
| 推送远端 | `git push origin main` |
| 线上检查 | 等 GitHub Pages/Actions 部署完成后访问线上地址 |

服务不可访问时的排查顺序：

| 检查项 | 命令/方式 |
| --- | --- |
| 端口是否占用 | `Get-NetTCPConnection -LocalPort 5174` |
| Node 是否运行 | `Get-Process -Name node` |
| 页面是否响应 | `Invoke-WebRequest http://127.0.0.1:5174/` |
| 重启固定端口 | `npm run dev -- --port 5174 --strictPort` |
| 查看日志 | `vite-5174.log`、`vite-5174.err.log` |

## 五、AI 协作提示词模板

### 1. 需求评估

```text
背景：xxx
需求：xxx
请先评估方案，输出潜在问题、需要澄清的问题和建议的设计/实现路径。
必要时先问询，不要直接进入代码实现。
```

### 2. 设计思路整理

```text
正式进入代码实现前，先整理设计思路列表。
表头包括：序号、模块、功能描述、备注。
我确认后再写入 Figma 或文档。
```

### 3. 评审修改计划

```text
读取评审记录 md，整理修改计划。
表头包括：序号、建议、需求文档变更、设计稿变更、代码实现变更、备注。
先生成 md 文档，后续按序号执行。
```

### 4. 代码原型实现

```text
按照设计思路、设计规范、设计稿和需求文档，实现 React 静态原型。
要求本地可预览、可构建、可部署 GitHub Pages。
实现后启动本地服务，并进行浏览器级视觉自检。
```

### 5. 文档一致性检查

```text
检查需求文档是否还有遗留问题。
重点检查：操作流程、判断逻辑、页面字段、特殊状态、错误提示、数据来源、数据排序、边界值、默认值、交互效果。
不要新增一个独立章节，而是检查已有章节是否覆盖这些要点并直接修正。
```

## 六、常见风险与规避

| 风险 | 表现 | 规避方式 |
| --- | --- | --- |
| 设计稿和代码不同步 | 用户在 Figma 手动改了，但代码仍是旧交互 | 每次用户说“我更新了设计稿”，先读取并总结更新项 |
| 文档残留旧口径 | 仍出现旧字段名、旧文案、旧组件名 | 用 `rg` 搜索旧关键词 |
| 原型无法预览 | 端口没跑、服务自动换端口、Node 退出 | 固定端口启动并检查日志 |
| 评审意见散落 | 后续不知道哪些已完成 | 维护评审修改计划表 |
| 过早开发 | 交互规则未确认导致返工 | 先确认数据来源、权限、保存范围、异常逻辑 |
| 只验证构建不看页面 | 页面能 build 但 UI 错位 | 必须浏览器打开并检查关键状态 |
| Git 提交污染 | `.idea/`、日志、临时截图被提交 | 提交前 `git status --short`，只 add 相关文件 |

## 七、本次项目沉淀出的最佳路径

```mermaid
flowchart LR
  A["输入背景和截图"] --> B["AI 评估方案并澄清关键问题"]
  B --> C["整理设计思路表"]
  C --> D["写入或更新 Figma 设计稿"]
  D --> E["用户检查并直接改稿"]
  E --> F["AI 读取设计稿并总结更新项"]
  F --> G["同步需求文档"]
  G --> H["实现 React 静态原型"]
  H --> I["浏览器验收和逐条修复"]
  I --> J["内部评审"]
  J --> K["整理评审记录和修改计划"]
  K --> L["按计划同步需求/设计/代码"]
  L --> M["构建、预览、提交和发布"]
```

最终建议：把 AI 当作“产品助理 + 设计执行 + 原型工程师 + 文档校对”组合使用，但每一轮都要指定当前事实源和验收口径。产品经理负责业务判断和最终取舍，AI 负责结构化、同步、落地和验证。
